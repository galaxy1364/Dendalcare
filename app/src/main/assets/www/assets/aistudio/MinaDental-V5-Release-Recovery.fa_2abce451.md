## P0-01 — Asset graph & deterministic deployment
شاهد: gh-pages-dist/index.html خطوط 48 و 62 به ./assets/index-CBxX-3O-.js و ./assets/index-DhWjtE-M.css اشاره می‌کند؛ هر دو مسیر در SHA ممیزی 404 هستند، در حالی که فایل‌ها مستقیماً داخل gh-pages-dist موجودند. فایل vite.config.ts در closeBundle فایل‌ها را به ریشه gh-pages-dist منتقل می‌کند. یک قرارداد انتشار واحد انتخاب کن: ترجیحاً خروجی کامل Vite با ساختار اصلی dist/assets و base مناسب مقصد؛ یا بازنویسی کامل و آزموده تمام ارجاع‌های HTML/CSS/ESM/modulepreload/dynamic import برای ساختار flat. هیچ فایل هش‌دار را دستی تغییر نده. HTML و assets و manifest و SW از یک Build ID واحد و انتشار اتمیک تولید شوند. نسخه GitHub Pages root، gh-pages-dist، Vite preview و Android WebView بسته‌بندی‌شده را جداگانه بررسی کن. مسیر خام src/main.tsx در سایت استاتیک نباید اجرا شود؛ یک entrypoint قطعی برای هر محیط ایجاد کن. برای همه لینک‌های محلی و importهای مستقیم و پویا، تست بازگشتی existence/HTTP 200/MIME ایجاد کن. در گذار نسخه قدیم، chunkهای موردنیاز نشست‌های فعال را حفظ کن یا بازیابی نسخه کنترل‌شده داشته باش.

## P0-02 — Async state machine / timeout ownership
شاهد: src/lib/useRealtimeTable.ts خطوط 304–405، timeout با controller.abort() کل درخواست را لغو می‌کند؛ shouldAcceptTableResponse پاسخ لغوشده را رد می‌کند و return قبل از setLoading(false) رخ می‌دهد. برای هر درخواست generation ID و scope snapshot داشته باش. Abort ناشی از unmount/scope change را از timeout شبکه تفکیک کن. برای هر تلاش شبکه AbortController مجزا با deadline محدود و backoff دارای jitter ایجاد کن؛ parent abort فقط لغو منطقی کل عملیات. finally فقط برای نسل و scope فعلی loading را خاتمه دهد؛ درخواست قدیمی حق تغییر state یا کش نسل جدید ندارد. وضعیت‌های timeout، error، offline، partial، unauthorized، migration_required و locked_offline صریح باشند؛ پاسخ خالی موفق empty است نه loading. تست fake timers + درخواست معلق، پاسخ دیررس، تغییر حساب، قطع اینترنت، pagination، retry exhaustion و StrictMode. برای refreshAll از allSettled یا قرارداد نتیجه ساخت‌یافته استفاده کن. UI shell و route navigation نباید به شبکه یا ۱۴ جدول وابسته باشند؛ تجمیع RPC و داده‌های ضروری را در اولویت قرار بده، از waterfall و دریافت تکراری جلوگیری کن. هیچ خطای شبکه را با داده ساختگی یا صفر واقعی جایگزین نکن.

## P0-03 — Service Worker & version coherence
public/sw.js و sw.js و index.html را یکپارچه کن. نام کش از Build ID واقعی تولید شود، نه نسخه ثابت v64.0-b64. فقط کش‌های namespace مینادنتال را مدیریت کن. هنگام انتشار نسخه جدید، نشست فعال را با skipWaiting ناگهانی وارد ترکیب فایل‌های ناسازگار نکن؛ پیام به‌روزرسانی و reload کنترل‌شده حداکثر یک بار. برای navigation از network-first با timeout و fallback معتبر استفاده کن. در SW فعلی `caches.match('./index.html') || caches.match('./')` به دلیل truthy بودن Promise fallback دوم را اجرا نمی‌کند؛ هر نتیجه را await کن و همیشه Response معتبر بازگردان. cache کردن HTML به جای JS/CSS، 404 و پاسخ خصوصی ممنوع. فقط app shell و static assets مجاز cache شوند؛ PII/API/auth cache نشوند. به‌روزرسانی هر پلتفرم، cold boot، warm boot، offline و اتصال مجدد را تست کن. بازیابی نباید IndexedDB، اطلاعات بیمار یا صف عملیات آفلاین را حذف کند.

## P0-04 — Bootstrap / route failure containment
src/main.tsx، AppProviders.tsx، AppRouter.tsx و ErrorBoundary.tsx را بررسی کن. __minaAppMounted پس از render فراخوانی شده و معادل React commit موفق نیست؛ handshake واقعی از effect ریشه پس از آماده بودن UI انجام شود. برای startup/import errors پیام دقیق، retry محدود و حالت قابل بازگشت داشته باش. ErrorBoundary مسیرها با route identity reset شود تا خطای یک ماژول بقیه را قفل نکند؛ React.lazy rejected promise نیازمند راهبرد import retry معتبر یا reload یک‌باره پس از تشخیص نسخه جدید است؛ صرف setState کافی نیست. Suspense بدون پایان ممنوع؛ مسیرهای غیرمجاز پیام دسترسی و مسیر امن داشته باشند. state machine مستقل BOOTING → SHELL_READY → AUTH_RESOLVING → READY/DEGRADED/ERROR. Auth/RLS را برای رفع خطای نمایش دور نزن. نبود schema یا membership معتبر باید به صفحه تشخیصی بدون اطلاعات حساس منجر شود. کلید محرمانه یا اطلاعات بیمار در log ثبت نشود.

## P0-05 — Release gate evidence
npm ci، npm run typecheck، npm run build، npm test را واقعاً اجرا کن. .github/workflows/ci.yml فعلاً staging job دارای echo و exit 1 است؛ runner واقعی Playwright و staging RLS با داده مصنوعی و حساب‌های محدود جایگزین شود. اگر محیط یا secrets موجود نیست، NOT RUN اعلام کن، نه PASS. تست Playwright روی artifact منتشرشده: root load، dashboard، patients، appointments، finance، services، lab، implants، reports، back/forward، refresh deep link، تغییر نسخه، offline/reconnect، 404 chunk، timeout، تغییر حساب/شعبه. تست Chromium و WebKit و Android WebView؛ دستگاه iOS واقعی برای قابلیت‌های بومی. ابعاد 360×740، 375×812، 390×844 و 430×932؛ scrollHeight/clientHeight، بدون بریدگی. ثبت console errors، failed requests، network timings، screenshot، و شناسه commit/build. هدف لود shell سریع مستقل از شبکه، بدون spinner بی‌نهایت و بدون خطای import. تست RLS و migrations جدید ابتدا روی staging و سپس با مجوز و backup؛ هیچ جعل داده/تضعیف امنیت.
